Yesterday (July 22) I was trying to make a `Dockerfile` for arm for a Go project, since this one cannot be compiled for ARM (depends on libpcap from the system). Before trying to do it in my Raspberry Pi - because it's kind slow do this things on it - I wanted to look how some images are made for arm. Because of this, I went to the `golang` package for armv7 and I found this Jenkins: [https://doi-janky.infosiftr.net/job/multiarch/job/arm32v7/job/golang/][2]. If you click on the link, you will see a Jenkins with x86_64 nodes with some virtual machines (more or less).

## binfmt_misc

I though "Well if these people can make docker images from Intel/AMD CPUs, there should be something to make it work... 🤔". _Googling_ a bit, I end up with these post "[Building multi-arch docker images][3]". The post starts saying something about manifests - you can look for them on the internet, seems really impressive - and how to get it work on Docker (and then says that it is already there). But, after this, `binfmt_misc` appears. WHAT IS THIS!?!?!??? After that, the post says that _Docker for macOS_ already has support for this. _Really?_ I could not believe that. ## QEMU at rescue

A couple of hours after, I googled about `binfmt_misc`. It is a Linux kernel's module that (in general) comes bundled in all the builds of the kernel. Allows the kernel to run arbitrary non-native binaries through an interpreter. I guess that module is what allows you to run a script (with the she-bang) as an executable and knows how to do it perfectly. "[Transparently running binaries from any architecture in Linux with QEMU and binfmt_misc][4]" is what I found. This post clarified me about everything. It's not about Docker, it's about the module, that allows to run arbitrary binaries (and so, Docker could simply take advantage of it). It's a good post, read it and then come again to mine's.

How I did to run the Raspberry Pi `echo` (in fact, I did not get it run, but at last not failing with "weird binary format" error). As I'm on Arch, I look for packages with `binfmt`. This was the right thing [`binfmt-qemu-static`][5], just what I want - I thought. When installing, recommends you to install [`qemu-user-static`][6] too, so I did. The first package allows you to register the formats into `binfmt_misc` (the same thing that the docker image does from the post from above). The second one are the qemu binaries. With a restart (or maybe with `sudo systemctl restart systemd-binfmt`) you can run arm binaries without any problem. So I decided to try again with my container of Debian. Again, the same error, even though I can run arm binaries now.

 > **Note**: at the end `binfmt-qemu-static` won't be needed.

 > **Another note**: on Debian/Ubuntu, I suppose that with `qemu-user-static` (not `qemu-user`) is enough to get the emulators. Don't install `qemu-user-binfmt`.

Meanwhile, looking in the _glorious_ Arch Linux wiki, I found that to enable custom binary formats, `none  /proc/sys/fs/binfmt_misc binfmt_misc defaults 0 0` should be written in `/etc/fstab`. I didn't check if that's not needed, but I wrote that. In addition, I tried the debian+python image from before, but mounting `qemu-arm-static` to see if it works, and:

## "Reverse engineering" to Docker for Mac

I though if it is possible to access to the VM inside hyperkit, maybe I could find something useful. Searching for it, I found this [incredible StackOverflow answer][7]. Well, I have to say this `screen` is quite bugged (you can't scroll), but it works, you can do things on the VM. Doing some `ls`s found this (literally this way):

<StyledImage
  src={image4}
  alt="Hyperkit's VM with some interesting content"
  fit="none"
/>

Reading `config.json` said that in `/etc/binfmt.d/` the kernel's module will find the configuration. I look for it and it doesn't exist. Then I noticed the `rootfs` and I looked inside it and it was there:

<StyledImage
  src={image5}
  alt="Configuration for binfmt_misc"
  fit="none"
/>

Only three entries: ARMv8 64 bit, ARMv7 and PowerPC 64 bit Little Endian. After that, I quickly compared the content of this file with the one provided by the `binfmt-qemu-static` package. For the shared entries, they were similar except for the end: the VM had an `CF` at the end. According to the [kernel's documentation][8], that sections means `flags`. The `C` is related with credentials and permissions (I guess), but the `F` is interesting: disables lazy loading of the interpreter. My understand that by enabling this, the interpreter can load before the containerization of the process, and so, the kernel can find the installed binaries on the system (the real one).

## Summary steps

To get docker run containers for other architectures you need to follow these steps:

  1. Install qemu emulators:
    - **On Arch Linux**: Install [`qemu-user-static`][6] or [`qemu-user-static-deb`][9]
    - **On Debian/Ubuntu family**: Install `qemu-user-static` (not `qemu-user`).
  2. Create a file on `/usr/lib/binfmt.d/qemu-static.conf` and _copy & paste_ one of the files from above.
    - **Pay attention with the emulator's routes**, the first one uses non-static binaries and the second, the static ones.
    - Modify the routes to match the installed ones.
  3. Reboot your computer
  4. Try something like `docker container run --rm -it armv6/alpine uname -a`
